给 Agent 补一层操作系统

DeepSeek Super-agent 技术报告 · 思想、业务流程与适用场景

原文《Super-agent 设计探索：迈向更自主的 Agent 系统》｜DeepSeek Harness 团队｜2026-10-31 20:29｜原型仓库 deepseek-ai/dsh-superagent-prototype

核心判断：Super-agent 不是在把模型做得更强，而是在给 Agent 补一层操作系统。它赌的是——当单任务能力不再稀缺，稀缺的是「人来管 AI」的带宽。于是它做了一件反直觉的事：把 Session 从产品界面降级为内部实现细节，让系统去承担调度的脏活，把人往上推到目标设定与验收。
阅读前提：这是一篇面向工程实践的架构思路探讨，不是产品发布。作者在开头和仓库 README 里都明确写了——不是官方产品、不是生产可用软件，公开版本与内部运行版本存在差异，文中部分特性仍在开发中。把它当架构论文读，不要当产品评测读。

一、问题：瓶颈换位了

过去一年，Coding Agent 已经证明模型能用工具解决复杂问题，而且越来越不需要人逐步盯着。但人的注意力没有跟着涨——一个人通常只能同时跟进 3 到 5 个活跃 Session。

而现有主流 Agent 的工作模式仍然以单一 Session 为基本单位，Session 之间彼此独立。你上午在群聊里讨论一个需求，下午去 GitHub 审 PR，中间那段上下文得靠你自己记住。于是出现了两条完全不同的天花板：

原文还点了三个非常具体的损耗，都是工程人熟悉的痛：

  • 单会话同步阻塞。一个 Session 在跑长任务，你在里面发的新指令只能排队，或者干脆打断它。
  • 多任务上下文混乱。靠 CLI、MCP、外部连接器把本地 Agent 扩起来，也解决不了跨 Session 的上下文同步——那是人要手动搬运的。
  • 设备离线即停。Agent 跑在你电脑上，合盖就断。

二、思想：把 Session 降级为实现细节

整套设计最核心的一句话，是「将会话管理与上下文同步从人手上移到系统层面」。翻译成工程语言：Session 不再是一个产品概念，而是系统内部的实现细节。用户面对的始终是「一个助手」，背后可能同时跑着五个会话。

人因此上移一层：从「逐步干预执行」变成「设定目标 + 验收结果」。作者把这个形态和它的系统架构合起来称作 Super-agent，并归纳成四条基础特征。这四条不是形容词，每一条都对应一个具体的工程模块：

特征含义靠什么撑住
连续用户在 IM 和 GitHub 里跟同一个 Agent 交互，感受上始终只有一个 AgentRouter 常驻 + 全局上下文 + Thread 归属
高效多任务并行推进，且不阻塞新指令Worker 隔离上下文 + 异步 ReAct Loop
主动持续观察环境事件，不必逐条下指令就能推进值得处理的事事件驱动 + 两级过滤 + 投机执行
持久始终在线，异常后可自动恢复存算分离 + 外部 Watchdog
值得单独记住的一句：作者自己说，整套设计「并没有提出全新的理论，而是将计算机系统中经典的工程思想应用到了 Agent 系统的构建中」。这句话既是谦虚，也是这篇东西最值钱的地方——它把 Agent 问题重新框定成了系统问题，而不是模型问题。

三、架构：Router 与 Worker 的两层分工

双层设计的关键不是「分了两层」，而是怎么切：把「连续性」和「并发效率」这两件互相打架的事，拆给两个不同的层去各自负责。

Router：便宜但一直在

Router 是持续运行的全局协调节点，统一承接来自 IM、GitHub、邮件的交互，是全局的排序点、协调点和记忆。它不执行具体任务，甚至不需要带 Bash 工具。作者判断 Router 的活往往没有看起来复杂，用轻量模型通常就能平衡速度与效果。

还有一个容易被忽略的细节：Router 是单 Session 的，上一轮推理期间积压的多条事件会自动合并、批处理注入。这是它在「保持连续」的同时摊薄单个决定推理成本的方式。

Worker：贵，但只干一件事

Worker 拥有隔离上下文、挂载完整执行工具、专注单一任务。因为它直接决定任务结果和代码质量，通常需要当前最强的模型。Worker 之间互不阻塞；一个 Worker 可以自己拉起 Subagent，甚至可以本身就是一个 Agent Team，而上层 Router 对此无感。

这个切法的精妙之处：「连续」要求一个稳定、便宜、记得住全局的大脑；「并发」要求多个昂贵、隔离、专心干活的执行体。把两者混在一个 Session 里，必然一方拖累另一方——这正是现有 Agent 卡住的根因。

四、业务流程：一条 bug 反馈的完整旅程

架构是静态的，真正体现「自主」的是事件怎么流。这条链路有五个关键站点，每一站都对应一个设计取舍。

两级过滤：借用 Fast Path / Slow Path

真实群聊噪音极大，绝大多数消息不需要 AI 介入。所以先由程序做确定性筛选（来源、群组范围、白名单），存活下来的候选才交给大模型按策略判断。这是操作系统里经典的快慢路径拆分，工程上还有个额外好处：策略写在提示词里，改行为不用改代码。

订阅直通：把 Router 从转发器里解放出来

同一 PR、同一 IM 话题、同一邮件链下的连续事件归成一个 Thread。Router 由第一个事件创建 Worker 之后，该 Worker 订阅这个 Thread，后续事件直接投递，只有无人订阅的事件才回到 Router 派单。这一手直接决定了 Router 不会成为吞吐瓶颈。

投机执行：先做了再说

这是全文最有想象力的一段。作者引入了计算机体系结构里的投机执行：结果是否被采用尚不确定时，先在后台提前尝试，有价值就提交，没价值就丢弃。

DeepSeek 内部配置的策略是「静默复现并修复」——有人在群里反馈 bug，AI 先在后台复现、分析原因，确认问题确实存在并且找到简单修复方法之后才提交，否则保持安静。这个约束很关键：没有它，主动就会退化成骚扰。

同样的机制也能用在个人助手上：收到会议邀请，提前核对日程、整理资料、备好回复草稿——反正不花你的时间。

上下文当缓存管

Worker 的上下文窗口被当作 cache 来经营：Inline 把近期大概率要用的信息拉进窗口，Spill 把超出预算的内容留在窗口外只留引用。Trigger、Thread、Worker 各有唯一 ID，串成一张引用图，支持按需多跳检索。这样长任务不会因为上下文膨胀而崩掉。

五、工程支撑：让它在没人看着的时候也不死

存算分离

执行循环放在云端，会话状态存进数据库，本地只留一个轻量 daemon。电脑合盖、离线，任务照样继续跑。

外部 Watchdog

独立组件负责检查任务是否陷入无效循环，并尝试修复。把「自杀检测」交给外部，比让 Agent 自我反省可靠。

异步 ReAct Loop

执行耗时任务期间仍能响应新指令，不必等这一轮跑完。原文注明尚未默认开启。

事件合并注入

Router 在上一轮推理期间积压的事件合并批处理，既保持连续，又把多个决定的推理成本摊薄。

六、实验数据：快了多少，代价是什么

团队做了一次消融实验，同时灌入群聊和 GitHub CI 两条消息流。单次运行约 300 条消息，其中约 20 条是工作请求；编码工作被替换成一个只消耗时间的工具，所以测的是调度与协作，不是单任务执行质量。消息间隔与工作时长按 1/4 缩放，模型调用延迟保持真实，每种配置重复 5 次。

数字背后的原因比数字本身更有意思：中性提示词下，模型五次运行里一次都没有主动调用 Subagent，所有工作都留在主会话，反复被新消息打断，于是 p95 拖到 29.5 分钟。换成「优先委派」的提示词后，五次里有四次成功委派，剩下那次模型判断「这活小，我自己干」，恰恰就产生了长尾。

这一点对做 Agent 的人最有现实价值：并发能力不是加一个 Subagent 工具就自动发生的。模型必须被显式鼓励去委派，否则它会倾向于自己扛——这是模型的行为偏好问题，不是架构缺陷。

账本的另一面也写在同一张表上：Super-agent 每次运行读取的 cache token 比单会话方案更多。这是它的固有成本——Router 常驻、Worker 多开、上下文多份，换来了响应速度和稳定性。所以它不是什么场景都划算。

七、适用场景：先看四个准入条件

与其罗列行业，不如给一组判断条件。同时满足以下四条，Super-agent 这类架构才有意义：

准入条件为什么是硬条件
有多个消息源事件驱动是它的引擎。只有一个入口、且都是人主动发指令，用单 Session 更省
任务可并行且互相独立Worker 的价值来自互不阻塞。强串行流程用不上第二层
环境能产生结构化事件群聊、PR、邮件、CI 都有明确的归属和 ID，才能做 Thread 与两级过滤
允许后台试错投机执行的前提是「白干一次」的成本可接受。强合规、不可回滚的操作不适合

三个已经被验证或明确点名的方向

已内部运行研发协作。这是 DeepSeek 自己的用法：基于该架构的内部实例已在日常研发中持续运行，参与问题复现与修复、代码审查响应，以及 DeepSeek Harness 自身的迭代。典型场景是——团队在群聊里讨论某个 bug，没人 @AI，它识别出潜在缺陷，在后台复现、找修复方案。

个人助手个人 Agent。原文的出发点就是 Personal Agent 集中涌现：直接接入消息、日程、邮件与工作平台，持续观察信息流并协助处理。会议邀请提前备料是它给的例子。作者特意说明，这种「持续在线 + 事件驱动」的模式并不局限于个人场景，个人助手只是其中一类。

跨平台同一条任务跨系统连续推进。一个任务在 IM 群聊里发起讨论，接着在 GitHub PR 里评审，再回到群里同步结论——全程对用户是同一个 Agent。这是「连续」这条特征最直接的使用场景。

不太适合的三种情况

  • 低频、单入口、纯问答。架构收益抵不过常驻开销，单 Session 更划算。
  • 强审计要求的流程。投机执行意味着会存在「做了但没采用」的中间状态，审计链要额外设计。
  • 环境给不出事件。没有结构化事件源，两级过滤和 Thread 归属都无从谈起，只能退回指令驱动。

八、边界：作者自己承认的四个难题

原文在结尾列了四个尚未解决的问题，这份坦诚比结论更有参考价值：

难题本质
系统可扩展性Router 是全局单点。订阅直通缓解了转发压力，但全局上下文与记忆仍是瓶颈
长期记忆Thread 结束后，Worker 的上下文怎么沉淀、怎么被下一次任务复用，没有给出方案
跨 Agent 通信多个 Agent 之间如何协商、避免重复劳动和相互踩踏，仍是开放问题
安全与隐私Agent 主动读群聊、读邮件、读 PR，权限边界与数据隔离如何设计
别忽略这句免责声明：公开的原型与研究原型并非生产可用软件，公开版本与内部版本存在差异，文中部分特性仍在开发中。把它当成一份架构设计参考，比自己照着搭一套要理性得多——尤其是当你的场景并不满足上面那四个准入条件时。

九、一句话总结

Super-agent 的价值不在于它让 AI 多做了多少事，而在于它承认了一个此前被所有人绕开的约束：人同时只能盯 3 到 5 件事。绕过这个约束的办法不是让模型更强，而是把「管理会话」这件苦力从人身上拿走，交给一层常驻的调度系统。

它真正提出的问题因此变成了：当执行不再稀缺，你的价值还剩下什么？原文给的答案是——目标设定与结果验收。这个答案对做 Agent 的人是架构启示，对用 Agent 的人，是职业提醒。
